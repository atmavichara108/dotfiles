# Горячая память v1 — исследование (И-10)

Заказ: сначала исследовать состоятельность подхода, потом спека. Позиции:
И-10 (это исследование) → И-11 (спека) → И-12 (реализация) → И-13 (автосейв
черновика) → И-14 (замеры).

Гипотеза заказчика: журнал (append-only, с принудительной записью на диск) +
индекс (ключ/путь/тег/время) + CLI (положить/взять/список/поиск); RAM — только
кеш, никогда единственное место.

## 1. Что уже есть (измерено)

| Механизм | Факт | Это журнал? | Это индекс? | Источник правды? |
|---|---|---|---|---|

Вывод по перекрытию: **диалоги** уже живут в базе и дублировать их нельзя;
**отправленные** промпты — в prompt-history; **события** — в handoffs и
session-reports; **образец журнала** у нас уже есть и работает (receipts-out).
Не хватает не «хранилища вообще», а **горячего состояния**: того, что ещё не
стало ни диалогом, ни документом.

## 2. Реальный пробел (то, что сегодня потеряли)

1. **Летучее состояние процесса**: черновик поля ввода, промежуточные решения,
   «что сейчас в руках». Живёт только в RAM клиента. Инцидент 2026-10-12 —
   прямое следствие.
2. **Нет единого адреса состояния.** Чтобы что-то найти, нужно заранее знать,
   где смотреть: база (sqlite-запрос), memory-файлы, handoffs, карточки, журнал
   писем. «Око» не может ходить «в любую точку», пока у этих точек нет общей
   системы ключей.
3. **Нет агентского интерфейса.** Субагент не может «положить» или «взять»
   состояние штатной командой — он читает файлы наугад.

## 3. Варианты и трейд-оффы

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **A. JSONL-на-сессию + производный индекс + CLI** | атомарный append без лока (образец уже в работе), нулевые зависимости, индекс пересобираем, легко чистить | нет транзакций; индекс надо поддерживать честно (дрейф) | **рекомендую для v1** |
| **B. SQLite (`hotmem.db`)** | транзакции, готовый поиск и индексы, конкурентная запись через WAL | второй тяжёлый файл рядом с 2,3 ГБ базой; больше машинерии; риск «второй правды» | во v2, если v1 упрётся |
| **C. Расширять базу opencode** | уже есть | схемой владеем не мы; V1/V2-наследие; запись только внутренностями opencode | нет |
| **D. Расширить mem-index (волт) до рантайм-состояния** | индекс уже есть | mem-index про **файлы**, не про состояние; писать в чужой репозиторий = лишняя политика | только как потребитель, не как база |
| **E. systemd-таймер + скрипт-выгрузка** | просто | не «горячо»: задержка минуты | как производный слой, не основной |

## 4. Узкие места (то, что определит дизайн)

1. **Цена fsync.** Принудительная запись — десятки миллисекунд на раз. Решение:
   fsync не на каждую строку, а на **смене состояния** (решение, отправка,
   закрытие верстака) + периодически; журнал сессии — без fsync построчно.
2. **Конкурентность.** Несколько сессий пишут одновременно. Атомарный append
   безопасен, пока строка **< PIPE_BUF (4 КБ)** и пишется одним `write`.
   Следствие: длинные тексты резать на записи ≤ 4 КБ (или на запись-манифест +
   файл-полезную нагрузку).
3. **Дрейф индекса.** Индекс — производное. В каждую запись индекса кладём
   смещение/хэш последней учтённой строки журнала; `hotmem doctor` сравнивает и
   говорит, что пересобрать. Индекс всегда можно убить и перестроить.
4. **Рост и ротация.** Ротация по месяцам в `journal/<YYYY-MM>/<session>.jsonl`;
   индекс хранит ссылку на сегмент, а не на «файл вообще».
5. **Секреты.** Журнал живёт **вне репозитория** (`~/.local/state/opencode/`),
   как receipts; в репо — только производные заметки. Фильтр на запись
   (переиспользуем опыт `input-security` и `garbage-guard`).
6. **Неизвестное:** даёт ли плагинный API V2 хук на изменение поля ввода. Это
   решает, будет ли И-13 (автосейв черновика) честным хуком или обёрткой.
   **Помечаю как открытый вопрос, не догадываюсь.**

## 5. Рекомендация для v1

**Что входит:**

1. Каталог `~/.local/state/opencode/hotmem/` (вне репо): `journal/<YYYY-MM>/<session>.jsonl`,
   производный `index.jsonl`, `doctor` для сверки.
2. Запись: одна строка JSON ≤ 4 КБ, атомарный append без лока; fsync на смене
   состояния, не на каждой строке.
3. Ключи: `key` (например `cell:registry`, `draft:ses_xxx`, `decision:ADR-024`),
   `tag[]`, `ts`, `session`, `scope` (repo/host/vault).
4. CLI: `put`, `get`, `list`, `grep`, `doctor`, `rotate` — в `scripts/.local/bin/`.
5. Правило: RAM — кеш; если чего-то нет в журнале, оно не существует для системы.
6. Автосейв черновика TUI (И-13) — как только выяснится вопрос с хуком.

**Что НЕ входит в v1:** SQLite-бэкенд, семантический поиск, синхронизация между
машинами, запись в репозиторий, индекс по чужим репозиториям, ретеншн-политика
сложнее месячной ротации.

## 7. Замеры, которые надо получить после v1 (И-14)

- время `get` по ключу против чтения реестра целиком;
- стоимость `put` без fsync и с fsync (перцентили);
- поведение при двух одновременных писателях (10k записей, проверка целостности
  строк);
- размер индекса против размера журнала;
- дрейф: сколько строк индекс теряет при аварийном завершении.
