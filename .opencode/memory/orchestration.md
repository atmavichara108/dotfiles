# Правила параллельной оркестрации

Заказ пользователя (basis: quoted, 2026-10-13): «можешь выполнять более масштабную
но аккуратную оркестрацию, ведь у нас уже куча субагентов?». Ниже — правила, по
которым это делается. Они же — чек-лист перед запуском волны.

## 1. Что вообще можно параллелить

| Тип задачи | Параллелится? | Почему |
|---|---|---|
| Read-only исследование (`researcher`) | да, свободно | не пишет, не занимает ветку |
| Верификация (`verifier`) | да, но она — про конкретный коммит/diff | вердикт привязан к состоянию дерева |
| Правки в **разных** файловых зонах (`meta` / `bash-dev` / `qtile-dev` / `util-dev` / `stow-ops`) | да, если зоны не пересекаются | одна ветка, один worktree |
| Правки в **одной** зоне | нет | конфликт коммитов и staging |
| Всё, что требует перезапуска конфигов | последовательно, в конце волны | иначе полдела не в силе |

## 2. Жёсткие ограничения

1. **Один worktree — одна активная ветка.** Параллельность достигается зонами и
   чтением, а не ветками.
2. **Не более 3 активных задач одновременно**, 5 — только если файловые зоны
   гарантированно не пересекаются.
3. **Субагенты не оркестрируют друг друга.** Иерархия плоская: primary → subagent.
   Только primary распределяет работу.
4. **Приёмка — не исполнитель.** PASS/FAIL выдаёт только `verifier`, и он
   независим от того, кто делал. Самоотчёт исполнителя — не приёмка (доказано
   2026-10-13: `meta` отчитался «потерь нет», `verifier` нашёл девять).
5. **Никаких «поисследуй всё».** У каждой задачи: вход, границы, deliverable,
   формат ответа, запрет на выход за scope.

## 3. Бюджет и модели

- Профильные прогоны — модель из `.md`; дешёвые (массовое чтение, разбор) —
  `opencode-go` (см. ADR-025).
- Модель субагента молча не подменяется. Упала модель — 2 повтора, потом стоп и
  доклад (не «сделать самому и выдать за результат субагента»).
- **Разбор и диагностика — не для flash.** Там, где нужна точность рассуждения (диагностика причин, сверка правил, разбор
  противоречий), модель не ниже среднего яруса. Flash-модели — массовое чтение и простая выборка. Инцидент 2026-10-13:
  отчёт исследователя на flash пришёл частично деградировавшим (смешанный язык, опечатки, неверные keysym-имена) и
  потребовал ручной перепроверки — то есть сэкономили токены, потеряли достоверность.
- Задачи не раздуваем: широкий бриф = шторм подтверждений (инцидент 2026-12-13
  с `researcher`: 10 команд, висящих в ожидании).

## 4. Права и подтверждения

- Каждому агенту — права под его реальные задачи (И-06): read-only наборы для
  исследователей, узкие allow-листы для исполнителей.
- Фоновые задачи не должны упираться в `ask`: если команда нужна штатно — она
  либо в allow-листе агента, либо задача оформляется иначе.
- Деструктивные операции остаются запретными независимо от «удобства» (ADR-024
  снимает бюрократию по мелочам, но не запреты на разрушение).

## 5. Завершение волны

1. Собрать отчёты всех задач волны.
2. Передать результат `verifier` (если были правки) — один вердикт на волну, при
   необходимости — повторная приёмка после FAIL.
3. Записать в инбокс/память: что решено, что осталось, чем доказано.
4. Перезапуск конфигов — один раз в конце волны, инициирует primary (ADR-026).
