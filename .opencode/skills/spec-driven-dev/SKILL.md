# Spec-Driven Dev — разработка по спекам

Правило закреплено **программно** (не «совестью агентов»):

| Слой | Что принуждает |
|------|----------------|
| `plugins/spec-write-routing.ts` | блок записи спеки проекта НЕ в его `docs/specs/` (роутинг спеки в нужную директорию проекта) |
| субагент `verifier` на другой модели (Р-109) | приёмка изменения — только вердиктором на модели, отличной от автора |
| `docs/specs/` (каждого проекта) | единый источник утверждённых спек; спека = описание, а не «реализация на лету» |

## Правила

1. **Спека → приёмка → вердиктор.** Любая реализация начинается с утверждённой
   спеки (или её черновика, который до реализации становится спекой). Код без
   спеки — отклоняется, сначала пишется спека.
2. **Спека живёт в `docs/specs/` своего проекта.** Запись спеки другого проекта
   в чужой `docs/specs/` или в волт — блокируется плагином `spec-write-routing.ts`.
   Маршрут: спека проекта → `<проект>/docs/specs/`.
3. **Правка вне спеки запрещена** без обновления спеки. Изменился поведение —
   сначала правка спеки, потом реализация.
4. **Приёмка = вердиктор на другой модели** (канон Р-109): исполнитель не
   принимает собственную работу. Вердиктор (`verifier`) даёт PASS/FAIL по
   критериям спеки. Модель вердиктора отличается от модели автора.
5. **Сухой прогон обязателен**: реальный запуск/проверка, не «синтаксис OK».
6. **Обходы исключительные и явные**: для функциональных правок обхода нет;
   несущественная косметика (комментарии, форматирование) может вноситься без
   отдельной спеки, но всегда с объяснением в коммите.

## Разграничение с соседними скиллами

- `spec-first` — резолв `spec-home` и блок `BLOCKED` без fallback (где лежит
  каноническая спека). Этот скилл — весь цикл: спека → реализация → сухой
  прогон → вердиктор на другой модели (Р-109).
- `parallel-coordination` — каналы хода (почта, ожидания, persist), а не
  разработка по спеке.

## Поток работы

1. Спека есть? Да → реализуй по ней. Нет → напиши спеку в `docs/specs/` проекта,
   получи приёмку ЦУ/владельца.
2. Реализуй. Правки — в зоне, описанной спекой.
3. Сухой прогон (реальный запуск).
4. Отправь на вердиктор (другая модель). PASS → приёмка; FAIL → исправь по
   findings.
5. Один коммит = один сюжет (tree-hygiene), в `task/*`-ветке.

## Когда использовать

- Разработка/правка кода, конфигов, автоматизаций, спеки.
- Миграция моделей, рефакторинг, добавление функциональности.
- Любая работа, где результат проверяется (не одиночный ответ).

## Когда НЕ использовать

- Одиночный вопрос/ответ без изменений.
- Read-only исследование (researcher) — оно спеки не меняет.

## Запреты

- Писать код без спеки (кроме явного черновика, который сразу оформляется спекой).
- Принимать собственную работу самому (нужен вердиктор на другой модели).
- Править спеки вне `docs/specs/` своего проекта.
