# Spec First — разработка по спекам

Правило закреплено **программно** (не «совестью агентов»):

| Слой | Что принуждает |
|------|----------------|
| `/spec` (command) | резолвит canonical execution specs только внутри `spec-home` текущего проекта (`<repo>/docs/specs/`) |
| `AGENTS.md` (глобал) | Vault не хранит чужие спеки; локальные pointers не источник правды |
| недоступность spec-home | `BLOCKED`, без fallback на догадки/память |

## Правила

1. **Спека раньше кода.** Постановка с правкой, у которой нет спеки в `spec-home`, — сначала спека (короткий черновик в `docs/specs/`), потом код.
2. **`/spec` резолвит только локально.** Источник правды — `<repo>/docs/specs/`; волт/память/пересказ — не источники.
3. **spec-home недоступен → `BLOCKED`.** Никаких fallback на «примерно помню».
4. **Спека короткая и проверяемая:** цель, scope (файлы), критерии приёмки, границы. Без простыней.
5. **Изменение scope = новый proposal.** Расширил файлы/агенты в ходе — стоп, delta отдельным предложением.

## Поток

1. Постановка → `/spec <имя>` → читаешь canonical spec из `docs/specs/`.
2. Нет спеки → пишешь черновик по шаблону (цель/scope/критерии/границы) → валидируешь у владельца (один закрытый вопрос) → правишь по спеке.
3. Выполнение сверяешь с критериями спеки, не с памятью о разговоре.
4. Финал → критерии спеки + evidence (пути, коммиты).

## Когда НЕ использовать

- Мгновенный багфикс с очевидным корнем (симптом→repro→точечный фикс в `task/*`) — там канон Мастерской.
- Read-only вопросы без правок.
