# ship-mail — файловая шина писем между сессиями (пилот)

## Зачем

peer-comms (letter.sh) связывает доставку письма с чтением: доставка = запуск
полного хода модели в сессии получателя. Отсюда цена (каждое письмо ≈ ход модели),
вся механика ожидания (busy-check, очередь, TTL, drain-бюджеты) и класс сбоев
«ложное sent» (журнал пишется до запуска; сбой = потерянное письмо). Живые
инциденты 2026-10-23/24: два письма ЦУ → ДВ-Хаб потеряны при «sent» в журнале.

ship-mail разводит транспорт и чтение: **доставка = атомарная запись файла**,
чтение = получатель открывает ящик в начале своего хода. Ноль ходов модели
на доставку, ноль демонов, журнал как отдельная сущность не нужен — файлы и есть
истина. Статус письма = его место на диске: врать система не может.

## Протокол

- **Ящик**: `$SHIP_MAIL_HOME/inbox/<sessionID>/` (по умолчанию
  `~/.local/share/ship-mail`). Внутри — новые письма; `read/` — принятые.
- **Письмо** = один markdown-файл с YAML-шапкой (OKF): `type: Letter`,
  `from`, `to`, `title`, `ref` (опц.), `ts`, `id` + тело. Имя файла:
  `<сортируемый-ts>_<id12>__<from>.md`.
- **Идемпотентность**: `id` = 12 символов SHA-256 от «тело + отправитель + день».
  Дубликат по id в inbox или read → отказ (exit 3), второго файла нет.
- **Адресация — только peer-registry** (INC-18): и получатель, и отправитель
  должны быть в реестре, иначе отказ (exit 4). Реестр адресов не меняется —
  меняется только транспорт.
- **Атомарность**: письмо пишется во временный файл и переименовывается в ящик.
  Половинных писем не существует: файл либо есть, либо его нет.
- **Жизненный цикл**: `send` → лежит в inbox → получатель `show` (читает) →
  `ack` (файл переезжает в `read/`). Канонизация содержимого в память проекта —
  отдельный шаг получателя, письмо ей не является.

## Инструмент

`scripts/ship-mail.sh` — send / inbox / show / ack / status. Выходные коды:
0 ok · 1 usage · 2 нет файла · 3 дубль · 4 адрес вне реестра · 5 реестра нет.
Тесты: `tests/ship-mail.test.ts` (jest, 7 сценариев: доставка, идемпотентность,
разные id, inbox/show/ack, отказ вне реестра, отказ при отсутствии реестра).
Транспорт без модели → детерминированный → покрывается тестами полностью.

## Границы (что это НЕ)

- Не канал памяти: письмо не попадает в docs/decisions.md само собой.
- Не срочное прерывание: аврал — владелец или старый канал (run-инжект), не шина.
- Без аутентификации: подпись «кем» — это поле from, доверие как у peer-comms
  (одна машина, один пользователь). При выходе за пределы ноутбука — подписи.
- Не замена реестра адресов: peer-registry остаётся SSOT имён.

## Развёртывание пилота

1. Контур: две сессии dv-hub (Смотритель ДВ-Хаб, «командная работа»).
2. Правило обоих: **первый шаг хода — `ship-mail.sh inbox <свой id>`**;
   отработал письмо — `ack`.
3. Параллельный прогон с peer-comms ~2 недели на живых письмах.
4. Взлёт в канон (глобальный/единственный канал корабля) — по слову владельца
   через ревью УАС/ЦУ; при положительном решении инструмент переезжает из
   dv-hub/scripts в общую зону (dotfiles), протокол — в канон корабля.

## Критерии приёмки пилота

- Обмен между двумя сессиями без единого хода модели на доставку.
- Владелец читает любые письма как обычные файлы (cat/Obsidian).
- Класс «потерянное письмо» невозможен по построению (write-once + ack).
- Тесты шины зелёные в `npm run ci`.
