# Incident record — CopyQ: «исчезающие» записи буфера (ложная тревога «утечки паролей»)

- **Incident ID:** BF-20261013-01
- **ts:** 2026-10-13
- **error class:** unknown (прикладной UI-баг сторонней утилиты, не provider/tool)
- **source/tool:** copyq / clipboard-history (сторонний харнес)
- **route_state:** ready (доставлено в мастерскую как `INC-10` в реестре
  `dotfiles/.opencode/memory/session-reports/2026-10-10-bugfix-workshop.md`)
- **notification_state:** not_required (это отчёт-передача, не письмо; при доставке — `letter.sh`)

## Symptom

В окне CopyQ после копирования длинного текста появились и через десятки секунд
сами исчезли 5–6 записей из символов, визуально похожих на пароли (одинаковой
длины). Рудра заподозрил утечку паролей. Рассинхрон затрагивает отображение
истории буфера; содержимое не потеряно, но «прячется».

## Repro

1. Копировать в буфер длинный текст (у нас — ~17 КБ).
2. Параллельно в окне CopyQ видно несколько коротких записей одинаковой длины
   из `[A-Za-z0-9]`.
3. Через десятки секунд эти записи пропадают из списка сами, без действий.
4. В логе CopyQ при этом — ошибки чтения несуществующих файлов данных записи.

## Root cause

**Подтверждено (факт):**

1. **Баг «мёртвого индекса».** CopyQ держит запись в индексе, а её файл данных
   отсутствует; на чтении логирует `Failed to read file … .dat: Файл или каталог
   не существует` и роняет запись из списка. Повторяется **ежедневно ~23:40–23:45**
   (в логах — серии за 10-04…10-06 и 10-10), один и тот же «мёртвый» id
   перечитывается сотни раз. Это и есть механика «появились → исчезли».

**Гипотеза (не подтверждена):**

2. Записи были **транзитными** — CopyQ не сохраняет на диск элементы, помеченные
   приложением-источником как «secret» (`x-kde-passwordManagerHint`) либо иначе
   невалидные; поэтому в персистентном хранилище их нет и восстановить нечего.

**Опровергнуто в ходе расследования:**

3. **Это не пароли.** Совпадающий по формату токен `buxrrn8Mou2VJH` (14 символов
   `[A-Za-z0-9]`) встречается в системе ровно один раз как **заголовок окна**
   в логе X-сессии; все прочие вхождения — артефакты самого поиска (команды
   расследования, записанные в логи/БД opencode). Формат совпадает с
   идентификаторами opencode: из ~1400 id в хранилище shell-выводов почти все
   имеют суффикс **ровно 14 base62-символов**. Единая длина как раз подпись
   генератора id. Паролей нет.

## Fix / workaround

**Сторонний харнес — не патчим** (правило incident-fix: чужой харнес → workaround
+ запись-факт + майнинг апстрима). Предлагаемый объём для мастерской:

- **A. Ремонт индекса (workaround, точечно).** Почистить/пересобрать историю,
  убрать «мёртвые» ссылки (очистить проблемный элемент/историю), подтвердить,
  что ошибка `Failed to read file` перестала повторяться в логе.
- **B. Харденинг конфига CopyQ** (`dotfiles/copyq/.config/copyq/`): включить
  игнор secret-элементов, задать лимит истории, при желании — автоочистку/
  шифрование элементов (GnuPG-плагин уже присутствует в командах). `[проверить:
  точное имя опции ignore-secret в CopyQ 16]`.
- **C. Диагностика (остаточный вопрос).** Устойчиво ли воспроизводится
  «прятанье» записей; если да — сузить до конкретного шага (возможно, апстрим-баг).

**Дизайн-требующий пункт** — вынести отдельной задачей с ID (`proposed` до
approval), не чинить «на лету».
