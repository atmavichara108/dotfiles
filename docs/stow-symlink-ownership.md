# Stow признаёт только относительные ссылки (гранит)

> Статус: высечено 2026-09-30. Источник правды первичнее этого файла —
> исходники GNU Stow (`find_stowed_path`) + живой дифференциальный тест ниже.
> Если stow обновится и поведение изменится — перепроверить, а не верить камню.

## Правило одной строкой

Ссылка с **абсолютным** путём (`-> /home/...`) для stow навсегда чужая.
Своими stow считает только **относительные** ссылки внутрь stow-директории.
Исключений и флагов не существует.

## Механизм (почему так, однозначно)

Проверка владения в исходниках stow дословно: если назначение ссылки
начинается с `/` — ссылка не может принадлежать stow, возврат пустоты,
дальше неминуемый конфликт «existing target is not owned by stow».
Это не эвристика и не баг, а сознательная защита от затаптывания:
абсолютная ссылка может вести куда угодно, stow её не трогает никогда.

Следствия, которые тоже проверены, а не угаданы:

1. `--adopt` ручную ссылку-папку не лечит: adopt умеет только забирать
   отдельные файлы (переместить файл в пакет + перелинковать). Ссылку-папку
   он либо не признает, либо уволокёт саму ссылку в репозиторий. Не применять.
2. `--no-folding` не лечит: флаг меняет раскладку новых ссылок, а не признание
   чужих.
3. Ручная ссылка при этом полностью рабочая для программ: ядро резолвит
   абсолютный и относительный путь одинаково. Ломается только управление
   через stow, не жизнь.

## Живое доказательство (повторяемо)

- Пакеты с относительными ссылками (`alacritty`, `rofi`, `dunst`, `nvim`,
  `zsh`, `tmux` — все `-> ../dotfiles/...` или `-> dotfiles/...`):
  `stow -n <pkg>` чистый, exit 0.
- Единственная абсолютная ссылка во всём доме
  (`~/.config/qtile -> /home/rudra/dotfiles/qtile/.config/qtile`,
  создана вручную 2026-08-25): `stow -n qtile` стабильно упирается
  в «existing target is not owned by stow: .config/qtile».
- Рядом лежит хвост прошлой поломки (`~/.config/qtile.broken`) —
  археология подтверждает: этот узел уже ломали руками.

## Эталонное состояние (как должно быть)

Весь дом — ссылки stow-нативные: относительные, созданные самим stow
(через `./stow.sh` или `./add-package.sh`, который в конце вызывает stow).
Sanity-критерий: `stow -n <pkg>` молчит по каждому пакету из `stow.sh`.

## Починка узла qtile (процедура, только по отдельному ДА)

Опасно тем, что это живой конфиг оконного менеджера. Порядок строгий:

1. Бэкап: зафиксировать текущее назначение ссылки (`readlink`) и убедиться,
   что содержимое папки побайтово равно пакету в репозитории.
2. Снять только ссылку (`rm` по самой ссылке — цель не затрагивается),
   затем обычный `stow qtile` (НЕ `-R`, НЕ `--adopt`): при отсутствующей цели
   stow свернёт дерево в одну относительную ссылку сам.
3. Проверка: `stow -n qtile` чистый; содержимое доступно; перезагрузка
   конфига qtile без ошибок.
4. Откат при любом сбое шага 3: вернуть ручную ссылку одним `ln -s`
   с захардкоженным путём из шага 1 — функционально эквивалентно,
   qtile разницы не заметит.

## Запреты навсегда

- Не создавать руками абсолютные ссылки на управляемых путях (`ln -s /home/...`).
  Новую ссылку всегда создаёт stow, не человек.
- Не лечить конфликты владения флагами (`--adopt`, `--no-folding`, `-R`
  поверх чужой ссылки) — сначала понять владельца через `readlink` + это правило.
- Здоровье проверять сухим прогоном: `stow -n <pkg>` перед любым применением.
