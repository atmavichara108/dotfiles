# Incident record — письмо ушло в фантомную сессию, read-gate дал ложный PASS

- **Incident ID:** INC-18
- **ts:** 1792349600 (2026-10-18 21:54)
- **error class:** address-error / false-positive-delivery
- **source/tool:** `tools/peer-comms/letter.sh` + `delivery-check.sh` (канал писем)
- **route_state:** resolved-fix (письмо доставлено повторной отправкой); системная часть — open
- **notification_state:** n/a (само-пойманная ошибка ИЦ; доклад владельцу сделан)

## Symptom
Письмо ИЦ → координатор («Control top») легло в **автосозданную сессию-фантом**, а `delivery-check.sh`
вернул `DELIVERED` (совпал hash) — при том, что реальный адресат письма не получил.

## Repro
1. Отправка по укороченному id (26 знаков вместо 30):
   `letter.sh --to ses_ed5fcec4effeZKwSoEmMe6 …` → в журнале `sent` + `run-rc=1`.
2. `delivery-check.sh ses_ed5fcec4effeZKwSoEmMe6 219b40700953522b` → **DELIVERED, seq=4**.
3. В `session_v2` появляется новая сессия с тем же префиксом и заголовком, сгенерированным из текста
   письма (`ts 21:54:26`), рядом с живой сессией-адресатом.

## Root cause
1. **Промах адресации (исполнитель):** id был взят из укороченного вывода SQL-запроса (`substr(id,1,26)`),
   а не из полного id. Класс уже фиксировался ранее («опечатка в session_id даёт успешную доставку в
   фантомную сессию, seq=4»).
2. **Канал не валидирует адресата:** `letter.sh` передаёт id как есть; OpenCode молча создаёт сессию по
   несуществующему id — фантом рождается из самой отправки.
3. **Read-gate измеряет не то:** `delivery-check.sh` сверяет наличие текста в реестре указанной сессии
   и потому даёт PASS на фантоме. Признак `seq=4` (микроскопический реестр) — единственная улика.

## Fix
- **Немедленный (сделан):** повторная отправка на полный id `ses_ed5fcec4effeZKwSoEmMe6Swlk` →
  `DELIVERED seq=22518` (реестр адресата: 3045 сообщений). Фантом переименован в
  «[ФАНТОМ] промах адресации ИЦ 2026-10-18 — не использовать (укороченный session_id, INC-18)».
- **Правило ИЦ:** id адресата берётся только полным (никаких обрезанных выводов запросов); перед
  отправкой — сверка адресата с `session_v2` (точное совпадение).
- **Класс (в R5 Lineage, критерий приёмки):** pre-send гейт `letter.sh` — резолв адресата по `session_v2`
  (отказ при отсутствии id и при неоднозначном префиксе) + пометка `addressee-verified`; read-gate
  сверяет адресата (заголовок/маркер сессии), а не только hash. Плюс метрика Lineage: «фантомные
  сессии» (сессии с микроскопическим реестром и заголовком из письма) — измеримый сиротский класс.

## Evidence
- v1 (промах): `sent 219b40700953522b…` → `run-rc=1`; `DELIVERED seq=4`; фантом
  `ses_ed5fcec4effeZKwSoEmMe6` @ 21:54:26.
- v2 (верно): `sent dcb466ccebed6873…` → `DELIVERED seq=22518` в `ses_ed5fcec4effeZKwSoEmMe6Swlk`.
- Реестры: адресат — 3045 сообщений (max seq 22520); фантом — 4 сообщения.
- Живой процесс-свидетель (те же 5 минут): сторонняя сессия отправляет письма в ЦУ с явной моделью
  (`opencode run -s ses_eceb23a7… -m nvidia/z-ai/glm-5.3`) — канал к ЦУ в работе.

## Status
`closed-fix` по конкретному случаю; системная часть (`pre-send` валидация адресата + честный read-gate)
— `open`, заходит в R5 Lineage (тот же гейт, что и класс «delivered ≠ processed», INC-17).

## Не баг, а фича
- has-feature-potential: true
- feature-evidence: класс «фантомный адресат» измерим и полезен Lineage — фантомные сессии
  (микроскопический реестр + автозаголовок из письма) становятся отдельной метрикой сиротства
  рядом с «сессии без владельца».
