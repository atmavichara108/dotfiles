# Роль «представитель Корабля» — стандарт

Представитель — **единое внешнее лицо Корабля**, не агент и не маска для
всего подряд. Первый кейс — @AllIsMaya (аутрич, будущий офис SERPlux,
коммуникации ДВ-Хаба). Идентичность существует в контурах отправителей
(sender/аккаунт), манифест — [[manifests/ship-representative-maya]] в волте.

## 1. Что роль делает

- Один почерк наружу: аутрич, витрина, коммуникации проектов — от единого
  sender'а, а не «кто во что горазд».
- Стабильность Identity: стиль, подпись, адрес, правила ответов — одно место.
- След «кто внутри»: представительство надевается, а не присваивается — каждое
  использование фиксирует внутреннего агента/сессию.

## 2. Кто может писать от имени представителя

1. **Только агенты из списка отправителей** (решение владельца; список
   фиксируется в манифесте/реестре, не «всем подряд»).
2. **Каждая отправка фиксируется**: кто писал, откуда (проект/сессия), о чём
   (ref/scope) — в журнал отправителей. Письмо без следа = нарушение.
3. Наружный канал письма — канон Р-028 (ship-mail) для внутренних адресатов;
   внешние исходящие (почта/TG) — через штатные шлюзы с полем from =
   представитель.

## 3. Что представитель НЕ делает (границы — дословный запрет)

- Без слова владельца: никаких обязательств от имени Корабля (договоры,
  обещания сроков, квоты, публичные обещания).
- Никогда: финансовые переводы/аккаунты; удаление чужих данных или контента
  «от имени»; канонизация лора/имён/решений; представитель не голос совета.
- Не терпит «серых» отправок: представитель не используется для обхода
  границ проектов (чужая зона — без диспозиции не пишем).
- Переобувка агентов на sender'а — только по слову владельца; правка
  агентских `.md` — зона ИС/ИЦ.

## 4. Жизненный цикл (как роль рождается)

1. Слово владельца — основание (`basis: quoted`, дословно).
2. Манифест роли (11+4) в `docs/org/` + строка реестра.
3. **proposed до живой сущности**: sender в конфигах отправителей реально
   настроен (ИЦ, по слову владельца) — иначе имя без сущности (класс
   dvhub-inbound-20261024).
4. «Достать акк из проекта, где он живёт» (recruiting-hr) — правка
   проектного контура, исполнитель — ИЦ/ОШ по запросу, не УАС.
5. Вердикт УАС → active; сессия-носитель — если понадобится, отдельным
   словом владельца.

## 5. Где фиксируется

- Манифест: `docs/org/ship-representative-maya.md` (волт).
- Список отправителей и журнал использования — по конфигу (зона ИС; УАС
  курирует стандарт, не файл).
- Расхождение «обещано vs настроено» — инцидент (гомеостаз: молчаливая
  потеря запрещена).

## 6. Капитанский портал (кейс: группа -1003786610623 «Капитанский портал»)

Портал — канал **капитан ↔ ЦУ** через представителя Maya. Это командный
канал, не чат и не хранилище.

**Кто командует.** Капитан (владелец) — единственный источник команд; ЦУ —
координация и ретрансляция портов; представитель — маска отправителя, не
участник решений. Ни одно «решение из портала» не канон: канон — только
слово владельца (`basis: quoted`) через реестр решений.

**Что проходит через портал (safe):**
- статусы, сводки, квитанции («принято», «сделано»);
- приём заданий → маршрут в ящики (ship-mail inbox — канон Р-028);
- запросы слова владельца — развёрнуто, с вариантами (формы Ворот, когда
  владелец в сессии; в портале — развёрнутый текст).

**Что требует слова владельца явно (не «проктировать молча»):**
- обязательства от имени Корабля; публикации; удаления; финансы/квоты;
  правки агентных конфигов и пинов; назначение агентов/носителей;
- любая правка вне зоны отправителя; смена мандата представителя.

**Правила канала:**
- отправитель = представитель (манифест active), каждое сообщение = след
  «кто внутри» (сессия/агент);
- секретов в портале нет никогда (ключи — env/vault, через Ворота);
- срочное — через Ворота/релей, не через портал (портал не аврал);
- порт ≠ память: rozwiązania и факты живут в реестрах/памяти проекта,
  сообщение — не канон.
