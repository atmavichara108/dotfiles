## 1. Отдел Приложений (ОП)

**Профиль:** поток создания самостоятельных полноценных приложений (образец потока — Мастерская, но там дефекты, здесь — создание). Правление: ЦУ и ИЦ (канон §1).

**Маршрут узла (этапы зрелости):**
| Этап | Форма | Где живёт | Выход на следующий |
|---|---|---|---|
| A. Контейнер-отсек | строка реестра отсеков + рабочая папка + **state-слой приложения (обязательный компонент: логи, квитки доставки, внутренние журналы — с ротацией; для почтового хаба — четырёхуровневый proof-of-delivery: SMTP-квиток с message-id, окно 48ч без отскока, DMARC-отчёты, подтверждение адресата)** | `~/Projects/apps-incubator/<app>` | спека приложения verified + каркас PASS |
| B. Свой репо | репозиторий в корне проектов + собственный агентский слой | `~/Projects/<app>` (свой `.opencode/`, AGENTS.md наследует глобальный канон, не копирует) | релизный маркер, стабильные циклы |
| C. Кластер | при >3 приложениях — кластер в корне проектов (модель SSA) | `~/Projects/<cluster>/<app>` | — |

**Клиенты (очередь):** 1) почтовый хаб (re-search.wiki, dv-hub; гибрид: максимум програмности + управление через почтового агента; внешняя часть — ИПТ по канону §10; прежний хендофф Лабы переносится в ОП **указателем на исходный документ до слова владельца, без копирования** — правило одного источника, сверка ИПТ mail-external-reconcile 2026-10-18; хостинг: Purelymail основной / MXroute резерв; ключи «владелец+клиент», агент хаба — draft-only). 2) И-36-справочник — по рекомендации §5 этой спеки.

**Права/швы:** не трогает чужие проекты; агентский слой приложения наследует конвенции из единого источника; созданные приложения не пишут в общие чекауты.

## 2. Отдел Движков (ОД)

**Профиль (канон §2):** подключение движков, полное обслуживание, обновления, сбор багов и предложений для разработчиков движка (наружу — программно, где можно). Операционный владелец формулы ADR-029 (6 артефактов: зона движка / dotfiles-пакет / SSOT-исходник / скрипт доставки / точка моста / строка реестра).

**Принимает в своё ведение (движковый слой dotfiles):**
- `docs/engines.md` — реестр движков и их зон (создан ADR-029, передаётся ОД по слову владельца §2);
- SSOT-исходники `opencode-global/.config/opencode/<engine>.jsonc` + sync-скрипты (`sync-mcode-config.sh`);
- мост T-156 (`opencode-serve.service`), дистрибутивы движков (`~/Applications/mcode/`), процедуры обновления.

**Процедура обновления движка (на примере первого дела — накат следующей версии мкода):**
1. Сверка версии/ченджлога апстрима; 2. Дистрибутив кладётся рядом со старым (откат не блокирован), sha256-проверка; 3. Живой старт (`mcode-open`) + smoke; 4. Сверка зон движка (namespace-миграции — по методу ADR-029 §1); 5. Обновление строки в `docs/engines.md` (версия/дата); 6. Свежие баги движка → реестр инцидентов ИЦ → наружу программно (issues апстрима, где включены).

**Права/швы:** правка движка запрещена (И-33); зона данных движка — read-only; заявки на новые движки = строка реестра + 6 артефактов (ноль копий конфигов).

## 3. Отдел Реверс-Инженерии Движков (ОРИД)

**Профиль (канон §3):** портировать лучшие релевантные решения чужих движков себе + добывать идеи для модернизации Корабля. **Основной навык — Панхарвестинг** (тотальный генеративный синтез: извлечение лучших архитектурных абстракций из разных сред, отсечение шума, пересборка в свою структуру).

**Артефакт-выход:** harvest-отчёт (волт `06-Audits/harvest-<env>-<date>.md`): среда → извлечённые абстракции → оценка релевантности по 7 критериям (метод fail-fast) → вердикт «портить / вдохновить / отсечь». Живая иллюстрация класса проблем (канон §5): 8 копий dotfiles в экосистеме — гиперреальность копий; ОРИД — тот, кто сводит копии к одному источнику.

**Права/швы:** strictly read-only (researcher-класс); первый кандидат-урожай — мкод (форк opencode: UI-решения, 32-path API, пайплайны обновлений).

## 4. Реестр стыков с внешним миром (приоритет 0, канон §4)

- **Файл:** `docs/external-interfaces.md` (dotfiles): стык | тип | владелец (отдел/роль) | что уходит наружу | права/бюджеты | статус.
- **Владелец-распорядитель:** кандидат от ЦУ — Отдел Приложений; **до слова Rudra** реестр операционно держит ИЦ, каждая строка помечена текущим держателем.
- **Правило:** стык без владельца не принимается (узкое место = потенциальный проёб); механизм отмирания — строка закрывается вместе со стыком.

## 5. Контрагент ранбуков + механизм свежести (канон §6, §11)

**Роль:** «Контрагент ранбуков» — именованная роль, владелец свежести операционного слоя (07-Runbooks волта + runbook.md проектов). Каркас роли — named agent в opencode-global (запускаемая сессия по необходимости); **шов с УАС:** каркас и механизм проектирует ИЦ сейчас, стандарты именования/онбординга канонизирует УАС после открытия (в спеке отмечено: стандарты — зона УАС, живой сессии нет).

**Механизм свежести (решение класса «сделано, но невидимо» — не переписывание ранбуков):**
1. **Машинно-читаемый признак:** frontmatter ранбука `covers: [инструменты]`, `verified: <дата>`, `owner:` — формат читается гейтом, но волт-файлы правит их владелец (либрариан/ЦУ), не гейт.
2. **Гейт свежести:** `tools/runbooks/freshness-check.py` (dotfiles): собирает реализованные инструменты (stow-пакеты, `scripts/.local/bin/*`, спеки done со статусом PASS/verified) → сверяет с упомянутыми в 07-Runbooks/00-INDEX/проектных runbook.md → **непокрытые выводятся списком, exit 1** (сигнал вместо тишины). Запуск: при /ship-классе приёмок и по запросу контрагента.
3. **Инверсия ответственности:** в чек-лист приёмки (verifier-контур ИЦ) добавляется пункт «новый инструмент упомянут в операционном слое» — шаг «сделано → описано» становится обязательным по факту приёмки.

**Текущий дефект закрывается этим же ходом:** helpctl/helpreg (33 записи) и hotmem v1 вносятся в покрытие (волт-правки — через владельцев волта; сигнал-список даст гейт).
