# Почта Корабля: протокол ship-mail (стандарт агентского контура)

Канон Р-028: почта Корабля — `tools/ship-mail/ship-mail.sh`, файловая шина.
Это стандарт агентского контура: как письма живут, адресуются, читаются и
гасятся. Инструмент и пилот остаются справочными; право следования — за
этим документом.

## 1. Транспорт vs чтение

Доставка ≠ чтение. Доставка = атомарная запись файла в ящик получателя
(ноль ходов модели, ноль демонов, ноль журнала: **файлы и есть истина**).
Чтение = получатель открывает ящик в своём ходе. Класс сбоев «ложное sent»
невозможен по построению: write-once + ack.

## 2. Протокол

| Элемент | Канон |
|---|---|
| Ящик | `~/.local/share/ship-mail/inbox/<sessionID>/`; `read/` — принятые |
| Письмо | один markdown-файл, YAML-шапка OKF: `type: Letter`, `from`, `to`, `title`, `ref` (опц.), `ts`, `id` + тело |
| Имя файла | `<сортируемый-ts>_<id12>__<from>.md` |
| Идемпотентность | `id` = 12 символов SHA-256 «тело + отправитель + день»; дубль → отказ (exit 3), второго файла нет |
| Адресация | **только через peer-registry** (INC-18): отправитель и получатель вне реестра → отказ (exit 4). Адреса из чата/памяти канона не создают |
| Атомарность | временный файл + rename; половинных писем не существует |
| Жизненный цикл | `send` → inbox → получатель `show` → `ack` → `read/`; **статус письма = его место на диске** |

## 3. Правило сессии (обязательное, с рождения)

1. **Первый шаг каждого хода сессии — `ship-mail.sh inbox <свой sessionID>`**;
   прочитанное — `ack`.
2. Отработал письмо — `ack` (файл уезжает в `read/`); молчаливых
   непрочитанных не оставляем.
3. Слово-ключ `ворота` (по регламенту ИЦ) — разблокировка чтения застойных
   ящиков при ремонте канала; не часть обычного протокола, аварийный жест.

## 4. Канонизация писем (архив Kanon)

Письмо **не является каноном и не памятью**. Архив `read/` — транспортный
след сессии (доказательство доставки). Канонизируется извлечённое: решение /
факт / цитата попадают в реестр решений или память проекта с `basis` и
ссылкой на письмо; тело письма туда не переносится.

## 5. Резервный канал

`tools/peer-comms/letter.sh` — **в резерве (deprecated)**: аврал и релей
владельца (run-инжект). Его честная доставка (`delivered`/`failed`/
`dead-letter`/`bounce` + входной гейт) — фикс 66cc05d. Снятие резерва —
совместное решение после стабилизации.

## 6. Онбординг ведомств

Новое ведомство получает правило «первый шаг хода = inbox» с рождения —
неотделимой частью стандарта онбординга (юрисдикция УАС, Р-004/Р-014).
Смена адреса в peer-registry — только через реестр + калибровочные письма.

## 7. Границы

- Не срочное прерывание: аврал — владелец или резервный канал.
- Без аутентификации: `from` — поле письма; одна машина, один пользователь.
  Выход за пределы хоста — отдельное решение (подписи).
- peer-registry остаётся SSOT имён: шина адреса не изобретает.

## 8. Доставка ≠ прочтение (свойства шины, подтверждено живым инцидентом)

- `DELIVERED` подтверждает **факт файла в ящике**, не факт чтения. Статус
  чтения = `ack`. Idle-сессия (владелец не в терминале, ход не запущен)
  признаков не подаёт — это природа pull-шины, не баг.
- Пробуждение idle-сессии: (а) Tab владельца + слово `inbox`; (б) релей
  резервного канала с осознанным флагом `PEER_COMMS_RESERVE=1` (журнал честно
  пишет failed/queued). Ожидать «ход случится сам» — нельзя.
- Срочное прерывание — только релей или Tab; шина для срочных не предназначена.

## 9. Письма пишем инструментом, не Write

Отправка письма = `ship-mail.sh send` (bash). Прямая запись в ящик из
write-инструмента чат-сессии — отказ по `external_directory` (инструмент
ограничен рабочим каталогом) и не штатный путь: письма пишем шиной, файлы
проекта — средствами проекта.
