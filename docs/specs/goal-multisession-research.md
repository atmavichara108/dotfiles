## 2. Что даёт «одна цель на несколько ведомств» (замысел)

Цель как **объект с участниками**, а не как личный слот:
`goal.json` (агрегат) + `goals/<goal-id>.json` (сама цель) +
`goals/<sid>.json` (вклад сессии: WIP, evidence, статус).

Потенциально закрывает классы дыр, которые сейчас лечатся перепиской:

1. **Перезапись цели** (Р-042) — исчезает: у каждой сессии свой вклад, у цели — один id.
2. **Оркестровка без бумаги**: сейчас «несколько ведомств на одну задачу» живёт в
   письмах и в голове координатора. Цель с участниками делает состав и статус
   каждого участника машинно читаемым.
3. **Связка план ↔ исполнение**: пункт плана (ЦСПиМ) может ссылаться на goal-id,
   goal-id — на ожидания (waits). Три звена становятся проверяемыми.
4. **Приёмка**: критерии цели видны всем участникам, evidence копится по сессиям,
   а не пересказывается в рапортах.
5. **Дрейф-детектор**: сессия-участник молчит дольше TTL → сигнал в сторож (тот же
   механизм, что `waits`).

## 3. Риски (то, что должно быть проверено, а не заявлено)

| Риск | Проявление | Чем снимается |
|---|---|---|
| Гонка записи | две сессии пишут в одну цель одновременно | запись только в свой вклад-файл; агрегат собирается на чтение |
| Разъезд «агрегат vs вклады» | агрегат говорит одно, вклады — другое | агрегат пересобирается, не редактируется руками; в агрегат пишет только сборщик |
| Цель без хозяина | цель создана, участники ушли | владелец цели + TTL молчания участника |
| Бюрократия вместо пользы | цель на каждую мелочь | порог: цель заводится на работу ≥2 ведомств или ≥N шагов (N=3) |
| Ложная полнота | «в цели» есть, а работа не идёт | статус участника (работает/молчит/сдал) как обязательное поле |

## 4. Пилот (предлагаемый, узкий)

- **Кто**: 2-3 участника на одной реальной задаче (кандидат — оформление репо
  почтового хаба: Apps-dev + ИЦ + ЦУ, либо формирование ЦСПиМ: ЦУ + УАС + ИЦ).
- **Что**: `<goal-id>.json` со списком участников и общими критериями; вклад-файл на
  сессию; команда чтения `goal show` собирает сводку «кто что сделал».
- **Критерии полезности (проверяемые)**:
  1. 0 инцидентов перезаписи цели за 7 дней пилота (сейчас — 1 случай за сутки);
  2. каждый участник видит общую цель и вклады остальных (чтение подтверждается
     выводом команды, не словами);
  3. хотя бы одна связка «цель → ожидание (waits) → пункт плана» пройдена end-to-end;
  4. сборка агрегата не зависит от порядка ходов сессий (проверка: две записи в
     разном порядке → одинаковый агрегат).
- **Останов**: если за 7 дней ни одна из связок не пригодилась в реальной работе —
  подход не подтверждён, возвращаемся к простому sidecar на сессию.
