> **Статус: `proposed`, НЕ approved.** Этот документ ничего не разворачивает и не
> даёт разрешения на исполнение. Он описывает, что и в каком порядке установит
> исполнитель (`sysop`, dotfiles local primary) ПОСЛЕ явного approval
> пользователя. До approval — только чтение и обсуждение. Эта задача — только
> подготовка спеки; реализация harness не входит в неё.

> описывает локальный overlay продукта. Обе спеки согласованы по модели
> «один primary `top` в каждом репо-корне» и общей границе control↔product.

## 2. Цель

Установить в `SSA/control/` минимальный, реально загружаемый control-plane
harness: канонический primary `top`, control-скоуп скилы и команды, карта
hooks/plugins (global-vs-local), модель доступа и границы репо, минимальные
runbook/задачи/роадмап/решения/проблемы/техдолг и артефакты приёмки. Harness
обязан проходить **живой smoke при открытии control-корня в OpenCode**, а не
только инспекцию конфигов.

Нель-цели (anti-goals): раздутый флот субагентов, дублирование общих определений
между control и product без версионированного источника, игровая терминология,
любой код продукта, любое реальное развёртывание.

## 3. Стратегия загрузки единого `top` (ядро задачи)

`top` должен загружаться как primary в ОБОИХ репо-корнях. Нельзя полагаться на
авто-подхват соседнего `.opencode/`. Исполнитель обязан сравнить варианты и
выбрать один, подтверждённый живым smoke.

### 3.1. Варианты (сравнить, выбрать, обосновать) **[derived]**

| Вариант | Как работает | Плюсы | Минусы / риски |
|---|---|---|---|
| A. Project-local `.opencode/` в каждом репо | Полная копия определения `top` в `control/.opencode/agent/top.md` и в product-репо | Гарантированная загрузка при открытии корня; изоляция | Дублирование определения; дрейф между копиями без синка |
| B. `OPENCODE_CONFIG_DIR` на общий каталог | Переменная окружения указывает на единый каталог определения `top` | Один источник правды; нет дублей | Зависит от окружения/direnv; при открытии «голого» корня без env — `top` не виден (нарушение требования 1.3) |
| C. Symlink/шаблон | `control/.opencode/agent/top.md` → симлинк на канон; product аналогично | Один файл-источник, видимость в обоих корнях | Симлинк может не трекаться/ломаться при clone; поведение резолва у OpenCode по симлинкам требует live-проверки |

### 3.2. Правило выбора

1. Выбранный вариант обязан обеспечить: открыл `control/` в OpenCode → `top`
   обнаруживается и работает БЕЗ ручной настройки окружения в сессии.
2. Если единый канонический `top` **нельзя** загрузить в обоих корнях без
   дублирования — это оформляется как **документированный decision gate**
   (`control/docs/decisions/0002-top-loading.md`, статус `open`), а не молчаливое
   размножение нескольких primary. Несколько primary без решения пользователя
   запрещены.
3. При дублировании (вариант A/C) обязателен **версионированный источник + синк**:
   канон живёт в одном месте, копии несут `source:` и `schema-version:`; дрейф
   ловится детерминированной проверкой (`tools/top-sync-check` — см. §5.4).

### 3.3. Обязательный живой smoke

Выбор не считается принятым, пока не пройден smoke §9.1 (открытие корня в
OpenCode, `top` реально primary). Инспекции файлов недостаточно.

## 4. Операционная модель control-plane (не просто список файлов)

### 4.1. Топология агентов

- **`top`** — единственный primary control-слоя. Роль: держать портфель, решать
  маршрутизацию, вести ADR/роадмап/задачи, инициировать bootstrap/оценку reuse.
  **[confirmed]** плоская минимальная сеть; субагенты — только по доказанной нужде.
- Субагентов на bootstrap control-слоя **не создавать**. Кандидатные роли
  (portfolio-review, reuse-assessor) фиксируются как `[open]` список, не runtime.
- Переиспользуемые глобальные субагенты (reviewer, verifier, researcher) —
  **не копировать** в SSA: они остаются в global/dotfiles-владении и вызываются
  как есть, если доступны (см. §6).

### 4.2. Control-скоуп скилы (минимум, по нужде) **[derived]**

| Скил | Назначение | Side-effects |
|---|---|---|
| `portfolio-registry` | читать/обновлять реестр портфеля (какие продукты, где repo, где spec-home) | запись только в `control/docs/portfolio-registry.md` |
| `bootstrap-assess` | оценка reuse при заводе нового продукта (что переиспользуется из модульного реестра) | read-only анализ + предложение, без создания кода |
| `module-registry` | реестр переиспользуемых модулей и их версий схем | запись только в `control/docs/module-registry.md` |
| `cross-status` | кросс-продуктовый статус/роадмап/задачи/решения свод | read по product-репо (только docs/статусы), запись в control docs |

Скилы детерминированы по side-effect: любое изменение файлов — только внутри
`control/` и точно перечисленных путей. Чтение product-репо — только docs/статус,
не код.

### 4.3. Control-скоуп команды (минимум) **[derived]**

| Команда | Что делает |
|---|---|
| `/portfolio` | показать портфельный реестр и статусы |
| `/newproduct` | мастер заведения продукта: создать repo-скелет-указатель, записать в реестр, предложить reuse (без кода продукта) |
| `/modules` | показать реестр модулей/версий |
| `/status` | кросс-продуктовый статус/роадмап/задачи/решения/проблемы/техдолг |

Команды — только оркестровка чтения/записи control-доков и вызова скилов; никакой
отправки, деплоя, платных эффектов.

### 4.4. Память / данные / SSOT

- **[confirmed]** SSOT памяти/данных и границы владения; без дублей между control
  и products.
- Control хранит: портфель, ADR, module-registry, кросс-продуктовый статус. Он
  **не** хранит спеки, код и данные продуктов (это зоны product-репо).
- Единственный кросс-репо указатель на product spec-home — поле в
  `portfolio-registry.md` (и карточка Vault, когда появится). Дублирование
  product-доков в control запрещено.

### 4.5. Карта hooks / plugins

- **[confirmed]** Глобальные hooks НЕ менять. Общие hooks остаются во владении
  dotfiles. SSA-специфика — только локально в `control/.opencode/`.
- Исполнитель составляет карту `control/docs/hooks-map.md`: что наследуется из
  global/dotfiles (имя, источник, назначение, «не трогаем»), что локально SSA
  (имя, файл, назначение, владелец SSA).
- Любой локальный hook SSA — детерминированный, без секретов, без сетевых
  побочных эффектов; документируется в карте.

### 4.6. Модель доступа и красные линии **[derived]**

- Точный scope репо: `top` пишет только внутри `control/`; читает product-репо
  лишь на уровне docs/статусов.
- Границы read/write ролей: primary — read+write в control; verifier/reviewer —
  read-only.
- Взаимодействие с git/lease: работа в `task/*`-ветке; `main` — только merge;
  горячие файлы — через существующие механизмы изоляции репо (если заведены).
- **Красные линии по секретам/ПД [confirmed]:** harness не читает секреты, креды,
  персональные данные клиента; verifier строго read-only и БЕЗ чтения
  секретов/ПД; deny на секреты/ПД сохраняется на всех ролях.
- Код продукта (`*.py`, `*.gs`, prod-конфиги) не читается и не меняется harness-ом
  без явной ссылки в отдельном подтверждённом scope.

## 5. Стадии исполнения (упорядочено; после approval)

> Все стадии выполняет `sysop` в `task/*`-ветке репо `control/`. Коммит/push/
> destructive git — только после отдельного explicit approval (HITL). Force push
> запрещён навсегда.

### 5.1. Стадия 0 — предпроверка
- Прочитать (read-only) актуальные `control/AGENTS.md`, `0001-bootstrap.md`,
  `portfolio-registry.md`, `docs/specs/README.md`, парную спеку product.
- Зафиксировать, что `.opencode/` ещё нет; завести `task/*`-ветку.

### 5.2. Стадия 1 — выбор стратегии загрузки `top`
- Сравнить варианты §3.1 на реальном окружении; выбрать один.
- Если без дублирования единый `top` не грузится в обоих корнях — создать
  `control/docs/decisions/0002-top-loading.md` (`status: open`, decision gate) и
  остановиться на этом пункте для решения пользователя. Не плодить primary молча.

### 5.3. Стадия 2 — установка `top` (control-корень)
- Создать `control/.opencode/agent/top.md` (frontmatter: `mode: primary`, модель —
  `[open]`/по правилу dotfiles, permission-блок с deny на секреты/ПД и
  destructive-операции, `dry_run`-ориентация).
- При варианте A/C — проставить `source:`/`schema-version:` и подготовить синк
  (§5.4).

### 5.4. Стадия 3 — скилы, команды, синк
- Создать control-скилы §4.2 и команды §4.3 (минимальный набор).
- Создать `tools/top-sync-check` (детерминированная проверка дрейфа копий `top`
  при дублировании) — только если выбран вариант A/C.

### 5.5. Стадия 4 — карты и модель доступа
- Создать `control/docs/hooks-map.md` (§4.5) и `control/docs/access-model.md`
  (§4.6).

### 5.6. Стадия 5 — операционные доки
- Завести минимальные: `control/docs/runbook.md`, `control/docs/roadmap.md`,
  `control/docs/tasks.md`, `control/docs/problems.md`, `control/docs/techdebt.md`,
  `control/docs/module-registry.md`. Решения — в существующем `docs/decisions/`.
- Обновить `portfolio-registry.md` при изменении указателей.

### 5.7. Стадия 6 — артефакты тестов/приёмки
- Создать `control/docs/acceptance/` с чек-листом §9 и шаблоном evidence.

### 5.8. Стадия 7 — gates
- На финальном staged tree: детерминированные/статические checks (узкие, по
  риск-профилю).
- Вычислить SHA-256 staged diff → reviewer → verifier (оба по одному и тому же
  hash). Любая правка после — аннулирует вердикты, gates заново.
- Коммит/tag/перенос — только после verifier PASS и explicit approval.

## 6. Границы и out-of-scope

- **НЕ** менять глобальные hooks и общие dotfiles-hooks (только читать/картировать).
- **НЕ** копировать global-субагентов (reviewer/verifier/researcher) в SSA.
- **НЕ** создавать субагентов control-слоя на bootstrap.
- **НЕ** писать код продукта, не трогать `*.py`/`*.gs`/prod-конфиги.
- **НЕ** дублировать product-доки/спеки в control.
- **НЕ** разворачивать ничего, не настраивать провайдеров, не слать писем.
- **НЕ** вводить игровую терминологию / Maya.
- Несколько primary без decision gate — запрещено.

---

## 7. Rollback

- Весь harness — новые файлы в `control/.opencode/` и `control/docs/`. Rollback =
  удалить добавленные файлы и `.opencode/` в своей `task/*`-ветке (reverse точного
  списка созданных путей) или не мёржить ветку в `main`.
- Так как глобальные/общие hooks не трогаются, системного состояния откат не
  затрагивает.
- Если выбран вариант C (symlink) и он сломал резолв — удалить симлинк, вернуться
  к decision gate §5.2.

## 8. Тесты / evidence

- **Детерминированные:** валидность frontmatter `top.md`; `top-sync-check` (если
  дубли) показывает отсутствие дрейфа; команды/скилы перечислены и ссылаются на
  существующие файлы.
- **Карты:** `hooks-map.md` сверён с реальным global/dotfiles-слоем (имена
  существуют); `access-model.md` не противоречит красным линиям §4.6.
- **Evidence:** артефакты в `control/docs/acceptance/` — лог открытия корня,
  список обнаруженных агентов/скилов/команд, вывод checks. Без секретов/ПД.

## 9. Acceptance (критерии приёмки)

### 9.1. Живой smoke при открытии control-корня **[обязательно]**
Открыть `control/` в OpenCode отдельно и доказать РЕАЛЬНОЕ поведение:
1. `top` обнаруживается и является primary (не текст в AGENTS.md).
2. Нужные control-скилы/команды видны и вызываемы.
3. Доки и границы репо корректны; код продукта не читается/не меняется без явной
   ссылки.
4. При дублировании `top` — `top-sync-check` зелёный (нет дрейфа).

Одной инспекции конфигов недостаточно. Затем reviewer → verifier.

### 9.2. Verifier
- **[confirmed]** Verifier строго read-only; БЕЗ чтения секретов/кредов/ПД; без
  read-deny по обычным файлам внутри точно перечисленного task-scope; handoff
  содержит точные пути, DoD, exclusions, evidence.
- **[open]** Эффективный внешний read verifier вживую НЕ подтверждён — это
  нерешённый acceptance gate. Не объявлять решённым; при неподтверждённом live-read
  приёмка не считается полной.

### 9.3. Решение по загрузке
- Если задействован decision gate §5.2 — приёмка требует зафиксированного решения
  пользователя в `0002-top-loading.md`.

## 10. Approval-гейты

1. Approval на исполнение этой спеки целиком (перевод из `proposed`).
2. Отдельный approval на выбор стратегии загрузки, если возник decision gate §5.2.
3. Отдельный explicit approval на любой commit/push/tag/перенос спеки в `done/`.
4. Расширение scope (новые скилы/команды/субагенты сверх §4) — новый proposal,
   прежнее согласие не переносится.

## 11. Открытые вопросы (сводка `[open]`)

- O1. Стратегия загрузки `top` без дублирования в обоих корнях (decision gate).
- O2. Модель `top` (ярус/ID) — по правилу dotfiles/пользователя.
- O3. Эффективный live-read verifier — не подтверждён.
- O4. Лицензия НЕ выбрана; различать права на код/модули, данные клиента,
  настроенную БД, развёртывание, модификации — открытый юридический вопрос.
- O5. Состав будущих control-субагентов — список кандидатов, не runtime.
